# Chapter 1 — 完成“霓湾·余晖街区”的首个可用版本

> 用法：将本文件与 `AGENTS.md` 放在项目根目录，让 Coding Agent 先读取 `AGENTS.md`，再完整执行本文件。  
> 本文件是可直接交给 Coding Agent 的第一阶段执行提示词。目标是产出可运行的 Godot 项目，而不只是再次输出方案。  
> 本阶段可以跨多个工作日完成；每日约 6 小时的 Agent 额度只是工作预算。

## 1. 你的任务

你是一名负责 Godot 工程、环境场景制作和性能优化的开发者。请依据根目录 `AGENTS.md`，实际构建项目“霓湾 / Neon Haven”的第一阶段。

最终交付：**Windows 本地运行的精美 3D 城市场景展示程序，拥有一张完整地图“余晖街区”、受限自由摄影机、三个固定机位、经济/均衡画质档，以及可验证的单地图加载和卸载架构。**

完成以下工作后再结束本阶段：工程构建、第一张地图美术、灯光、观察工具、生命周期验证、可进行的图形/性能检查、运行文档和后续交接。真正受环境限制的检查可标记待验证，并提供直接运行的入口；不得将它们写成已通过。

不要实现 NPC、人物控制、玩法、任务、车辆 AI、完整短剧系统、第二张正式地图或无缝开放世界。地图菜单和摄影工具属于允许的工具操作。

## 4. 工作包 A：工程外壳与地图生命周期

### A1. 主场景

创建 `scenes/app/main.tscn`，主要组成：

- `MapSlot`：唯一地图容器。
- `CameraRig`：单个 Camera3D 及观察控制器。
- `ToolUI`：地图、画质、机位、帮助和关闭 UI 的工具界面。
- `LoadingOverlay`：单纯 2D 遮罩与状态文字。
- `Diagnostics`：可关闭的调试显示和采样器。

默认启动自动进入 `m01_afterglow`；地图菜单用于查看当前地图和重新进入。进入菜单时允许保留当前地图，选择切换或退出地图后才卸载；菜单本身不能使另一张地图常驻。

主场景不持有所有地图的 PackedScene。地图环境由当前地图自身拥有，禁止多个 WorldEnvironment 相互覆盖。

### A2. 地图定义

实现 `MapDefinition`，字段遵循 AGENTS.md：`schema_version`、`map_id`、`display_name`、`scene_path`、`preview_path`、`default_anchor`、`camera_bounds`、`camera_exclusion_bounds`、`anchor_names`、`lighting_profile_id`、`available`。

创建：

- `maps/m01_afterglow/map.tscn`
- `maps/m01_afterglow/map_definition.tres`
- `data/map_registry.json`

注册表例子：

```json
{
  "schema_version": 1,
  "maps": [
    {
      "map_id": "m01_afterglow",
      "definition_path": "res://maps/m01_afterglow/map_definition.tres"
    }
  ]
}
```

`scene_path` 指向 `res://maps/m01_afterglow/map.tscn`。默认锚点 `street_view`；另外两个锚点为 `repair_shop_view`、`station_view`。第一张地图名称为“余晖街区”。

为不影响执行的描述字段选择合理默认值即可，不要为了字段命名反复询问用户。

### A3. 地图管理

按 AGENTS.md 的状态机实现 MapManager：

1. 先校验 ID 和路径。
2. 显示加载遮罩、停止摄影输入。
3. 停止并卸载旧地图，断开信号、清空强引用，等待节点删除生效。
4. 旧地图不在场景树后，再请求下一地图后台加载。
5. 只在资源加载完成后取回 PackedScene。
6. 主线程实例化，验证根节点与锚点、应用质量档、完成首次显示准备。
7. 恢复观察输入，更新 UI 和日志。

重复点击时只保留当前切换事务，按钮显示忙碌状态；第一版无需实现复杂队列或后台加载取消。

无效路径请求在卸载前被拒绝，当前地图不变。合法请求在卸载后加载失败时，保留可用的空外壳，显示错误和重试入口。退出程序时不遗留自行创建的工作线程。

只使用 Godot 后台资源加载接口，不为整个引擎场景树手写线程。`load_threaded_get()` 的调用时机必须避免意外同步阻塞。

### A4. 验收

- 启动时只有一张活动地图。
- 单独卸载后，活动地图数为零，工具 UI 仍正常。
- 重新载入恢复一张地图；没有旧环境、旧动画或旧摄影机残留。
- 加载失败不使程序永久停留在遮罩。
- 后续新增地图只需要新内容目录、定义与注册项，不复制整套程序。

此时可用少量占位建筑验证工程，随后必须在本章内替换为成品场景。

## 5. 工作包 B：地图布局与三个主构图

### B1. 地图空间

采用约 120×160 米的核心场景，中心接近世界原点。X 表示东西，-Z 表示北方。外围天际线可超出核心范围，只作本地图的简化背景。

初始布局建议如下，可在不破坏三个主构图的前提下微调：

| 区域 | 大致位置 | 内容 |
| --- | --- | --- |
| 主街 | X = -6…6，Z = -60…60 | 路面、标线、路沿，形成长纵深 |
| 两侧人行道 | X = -11…-6 及 6…11 | 灯杆、橱窗、少量街道家具 |
| 西侧楼群 | X = -45…-12 | 连续但不单调的住宅/商铺立面 |
| 东侧楼群 | X = 12…45 | 修理铺、住宅、独立主建筑 |
| 侧巷 | Z = -5…3，向西侧延伸 | 空调外机、管线、海报、安静空间 |
| 修理铺前广场 | X = 11…32，Z = 15…38 | 近景主场所，保留人物未来站位空间 |
| 修理铺建筑 | 广场东侧，约 X = 33…44 | 暖光橱窗、厚雨棚、结构清楚的店面 |
| 街尾站口 | Z 约 -60 | 高架结构、站名牌、横向视觉终点 |
| 远景 | 核心边界外 | 低细节塔楼、信号塔与城市轮廓 |

楼群必须避开侧巷和广场，不把表格中的整个区域填满。保留可读的空间关系。

建议初始摄影机整体 AABB：X = -50…50，Y = 1.5…24，Z = -70…70。为楼体添加简化禁入 AABB；不引入物理角色/导航系统。自由镜头移动只检查少量明确的边界数据。

### B2. 三个机位

下表的坐标是起始构图参数，允许现场调整；最终参数必须保存到 Marker3D，并记录在画面报告里。摄影机不允许贴入物体。

| 锚点名称 | 初始位置 | 观察目标 | 验收重点 |
| --- | --- | --- | --- |
| `street_view` | (-3, 1.7, 52) | (1, 8, -45) | 前景路沿、中景商铺、远景站口层次分明 |
| `repair_shop_view` | (15, 1.8, 31) | (33, 2.5, 25) | 店招、雨棚、门窗厚度、修理道具和暖光 |
| `station_view` | (18, 12, -35) | (0, 12, -62) | 高架结构与城市剪影，轮廓干净 |

摄影机 FOV 初始约 60°，以引擎实际属性和画面为准；固定画幅 16:9 验收。宽阔画面不能靠过大的广角制造严重拉伸。

每幅画面必须有一个清楚的视觉焦点。至少一条街道需要转折或遮挡，降低一次看到全部细节的成本。

### B3. 成品布局要求

- 约 12–18 个主要建筑体量，不要求每栋完整室内。
- 至少 3 栋在体量、轮廓、立面上明显不同的主建筑。
- 至少 6 种可识别的立面组合，允许基于少量模块变化。
- 至少 3 个可辨认的店铺门面，修理铺为最精细的近景主体。
- 一处远景地标：信号塔或高架站结构。
- 场景边缘通过围墙、建筑、道路弯折和背景体量自然收束；禁止明显地板悬浮在虚空中。

完成灰盒后立刻在三个机位检查比例、层次和遮挡。布局通过后再制作细节，避免精修最终看不到的位置。

## 6. 工作包 C：建筑模块、材质与细节

### C1. 第一批可复用模块

至少建立以下种类，具体文件可合理合并，避免为了达到文件数量拆分：

- 两类基础墙面与转角模块。
- 窗框、内缩窗面、窗台。
- 一类阳台和一类檐口/屋顶边缘。
- 店铺门框、浅景橱窗、雨棚。
- 地面路沿、排水沟、台阶。
- 高架支柱、横梁、站口标识结构。
- 空调外机、管道、箱体、长椅或街边椅子。

模块必须具有合理厚度与尺度。关键近景边缘使用少量倒角；重复小细节可通过纹理表现。屋顶/背面是否制作取决于实际可达机位，不能与相机范围冲突。

优先共享网格与材质。离线脚本可以生成模块和基础摆放，再保存为资源供编辑器精修。运行时不能在 `_ready()` 里重新生成全部建筑、贴图和 lightmap。

### C2. 材质组合

至少建立以下可分辨的材料类型：混凝土、涂漆金属、深色金属、窗面、砖/墙砖或面板、路面、发光招牌。

材料变化要在正常机位中可见：

- 金属有受控高光，路面高光宽而弱。
- 墙面能看到适当接缝和色差，但不铺满高频噪声。
- 旧化优先出现在底部、接缝、雨水路径和长期接触位置。
- 招牌亮度有限，不能把文字整片烧白。
- 橱窗主要使用浅景盒和受控材质表现深度；不制作复杂实时玻璃折射。

典型贴图 512/1024，关键店面可用 2048。使用贴图时检查 UV 和 mipmaps；不用超高分辨率纹理弥补模型/构图问题。

### C3. 中文招牌与资源来源

推荐招牌名称为“余晖维修”“霓湾站”“海风便利”。没有人物仍能通过这三个地点形成清楚的城市身份。

优先使用明确授权、可随项目分发的中文字体并附许可；可在制作阶段生成招牌纹理/网格。Windows 系统字体可用于本地制作验证，但未经许可不复制进发布包。

素材来自外部时记录来源和许可。找不到素材时用原创模块继续推进，不等待采购。不允许从现有商业游戏中提取模型、招牌或贴图作为默认方案。

### C4. 质量门槛

灰盒不算完成。三个主构图中，近景应至少同时具备：结构进深、表面材质差异、接触明暗、合理文字/标识、可解释的物件布置。

保留至少一组“灰盒→成品”截图，说明美术迭代确实发生。最终宣传/验收图必须从实际 Godot 场景获取，不能用生成式概念图替代运行画面。

## 7. 工作包 D：固定傍晚光照

### D1. 基础效果

- 天空为冷蓝到暖灰的傍晚过渡，建筑表面仍可辨认。
- 店铺窗内使用暖光，少量青色科技标识作点缀。
- 路面只在局部降低粗糙度，模拟雨后痕迹。
- 普通深度/高度雾只用来形成远景层次，不能遮盖整个街区。

### D2. 静态烘焙流程

1. 确认被烘焙网格具备有效 UV2、正确法线和尺度。
2. 遵循 AGENTS.md 的节点层级：`BakedWorld` 本身为 LightmapGI，需要烘焙的建筑、地面与道具在其子树内；实际检查烘焙结果没有遗漏。
3. 灯光先用低成本预览调整构图，布局稳定后再正式烘焙。
4. 将需要的直接/间接静态照明烘焙；检查运行时是否仍留下不必要的实时灯。
5. 保存 lightmap 数据、关联贴图、导入配置与需要的 unwrap 缓存。
6. 重开工程和导出后验证光照仍存在，不能只在当前编辑器会话有效。

烘焙以实际引擎能力为准。不要臆造“命令行一键烘焙”参数。如果只能通过图形编辑器完成，准备明确操作步骤，并在可用图形环境完成；当前环境不能执行时标记缺口，先交付其他已完成内容。

### D3. 低负担限制

- 经济档不启用额外实时局部灯、实时阴影、局部反射探针和粒子。
- 均衡档最多 2 个无阴影实时局部灯、2 个 Once 反射探针、2 个局部粒子发射器。
- 两档都保留主要 lightmap。不要靠关闭烘焙照明降低性能。
- 不依赖 Mobile 不支持的 SSAO、景深、SSR、体积雾或 SDFGI。
- 首次探针准备、资源上传等在遮罩期间处理并记录，不保证“后台加载=所有过程无卡顿”。
- 固定烘焙光照对应一个时间；本阶段不添加动态昼夜按钮。

## 8. 工作包 E：观察、画质与截图工具

### E1. 摄影机操作

| 输入 | 行为 |
| --- | --- |
| 鼠标右键按住 | 控制镜头朝向，释放后恢复 UI 指针 |
| W/A/S/D | 在观察模式下前后左右移动 |
| Q/E | 在观察模式下下降/上升 |
| Shift | 临时加速 |
| 鼠标滚轮 | 调整移动速度，限制合理上下限 |
| 1 / 2 / 3 | 切换三个固定机位 |
| Home | 回到默认机位 |
| F1 | 隐藏/恢复工具 UI |
| F2 | 显示/隐藏诊断面板 |
| F12 | 保存截图 |
| Esc | 释放捕获指针并打开/关闭工具菜单 |

移动速度初始 3 米/秒，加速约 9 米/秒；可在测试后调整。相机平滑与帧率无关，使用 delta，不依赖固定每帧位移。

输入被 UI 文本框/菜单消耗时，不让摄影机同时移动。窗口失焦必须释放鼠标，不出现重新聚焦后镜头突然跳转。

整体边界和建筑禁入 AABB 由地图提供，只在相机移动时检查。拒绝会穿过楼体的移动段或进行小步检查，避免高速跨越禁入区。机位切换使用保存的 Transform3D，不持有旧地图锚点节点。

### E2. 画质设置

严格实现 AGENTS.md 的 Eco / Balanced 两档；启动默认 Eco。允许调整帧率上限，但 UI 默认不提供“无限制”作为突出选项。

配置保存到 `user://settings.cfg`，不写回 `res://` 或源码文件。无效配置使用默认值。实际使用的渲染器要能在诊断界面查看，画质切换不改变渲染器。

失去焦点限制 10 FPS，最小化限制 5 FPS 并暂停环境动画；恢复后回到之前用户选择的帧率与动画状态。

### E3. 截图

- 保存为 PNG，路径为 `user://captures/`。
- 文件名包含地图 ID、机位或 `free_camera`、画质档、时间戳。
- 截图自动隐藏工具/诊断 UI，等待实际绘制完成后取图，然后恢复之前 UI 状态。
- 对重复按键进行节流；截图完成给出文件名和打开目录入口。
- 主视图截图不包含编辑器面板。另可保存一张带诊断的验证图，明确区分用途。

### E4. 预留内容

MapRoot 下保留空 `Reserved/ActorRoot`，命名三个稳定摄影锚点即可。本阶段不实现演员、剧本语言、时间轴编辑器、自由录音或视频编码器。

## 9. 工作包 F：性能与生命周期验证

### F1. 地图切换测试

在 `tests/fixtures/` 创建一个极小测试地图，使用不同地图 ID，只有简单几何、一个环境和一个测试锚点。它不进入生产注册表和发布地图菜单。

测试管理器允许从测试入口注入两张地图的定义，完成正式地图 A→测试地图 B→A 的 10 次往返。

验证：

- 任意时刻活动地图根节点数量不超过 1。
- 旧地图的弱引用失效，旧 Timer、Tween、音频、环境与地图节点没有残留。
- 重复请求不触发两个并发加载事务。
- 不存在先加载全部地图再隐藏的代码。
- 正常请求、无效 ID、缺失路径、缺失锚点各有明确结果。
- 切换后相机和质量档正确，不保留旧地图引用。

允许缓存共享资源；不把“内存没有立即降回完全相同数字”直接当成失败。出现连续增长时定位持有引用并保留记录。

### F2. 固定镜头路线

建立只用于验收的 60 秒路线，不做通用导演编辑器：

- 0–20 秒：主街机位附近缓慢向前，保持站口在纵深中。
- 20–40 秒：切换到修理铺机位并进行小幅横移。
- 40–60 秒：切换到站口高位机位，进行小幅平移观察城市轮廓。

机位间采用明确切镜，不能让测试镜头直线穿过建筑。使用相同时间进度驱动，保证不同机器/帧率下路线一致。

初次运行、预热和稳态测量分开。每个档位预热 15 秒后采集 3 次路线。为防止固定路线掩盖问题，再手动观察边界与复杂近景。

### F3. 输出指标

保存 `artifacts/performance/chapter1_metrics.csv` 和对应说明，至少包括：

```text
run_id, map_id, quality, renderer, build_type, engine_version,
window_width, window_height, render_scale, frame_cap,
average_fps, frame_interval_p50_ms, frame_interval_p95_ms,
frame_interval_p99_ms, stutter_over_100ms_count,
draw_calls_peak, map_node_count,
process_working_set_mib, gpu_memory_mib,
resource_load_ms, activation_ms, notes
```

CSV 实际生成时使用单行表头。缺少可靠采集能力的列填写 `N/A`，在 notes 说明原因；禁止用 Godot 静态内存值冒充 Windows 总工作集，用渲染内存估计冒充准确进程显存。

帧间隔必须来自实际逐帧采样，分位数基于保留样本计算；不要拿 `1 / average_fps` 同时填写所有分位数。诊断文字最多 4 Hz 更新，采样数据用轻量缓冲收集，结束后写盘。

目标沿用 AGENTS.md：Eco 平均 ≥29 FPS、P95 ≤40 ms；Balanced 平均 ≥58 FPS、P95 ≤20 ms。资源预算同样沿用根规范。未达标时定位瓶颈并记录，不擅自调整验收路线规避重场景。

### F4. 优化顺序

1. 检查是否存在意外加载其他地图、重复资源、未受限帧率或无用途逐帧循环。
2. 区分 CPU、GPU、资源加载、着色器首次准备的问题。
3. 减少过多材质/绘制批次；重复道具按局部区域实例化。
4. 调整遮挡体、LOD、小道具距离，做开/关对照确认收益。
5. 限制透明叠加、探针、灯光、粒子与 lightmap 体积。
6. 最后调整内部分辨率/局部资产细节，保留三个主构图质量。

不要未经测量就把脚本迁移到 C++，也不要直接更换引擎。

## 10. 工作包 G：画面复核、导出与交接

### G1. 画面检查

分别在 Eco / Balanced 档位获取三个主机位截图，共 6 张。检查以下问题并修复：

- 地面、路沿、建筑是否真正接触，没有悬空或严重穿插。
- 墙面、窗框、招牌是否有厚度和真实比例。
- 是否出现 UV 拉伸、反面剔除空洞、Z-fighting、严重漏光。
- 冷暖关系和亮度是否让主体清楚；发光文字是否可读。
- 远景是否连续，能否看出城市延伸，而不是空平面上几栋孤立楼。
- 近处店面有没有足够细节，远处是否避免无意义的微小几何。
- 经济档是否仍保留完整场景风格。
- 自由相机允许到达的区域是否会露出未制作部分。

原始截图保留，不进行会掩盖渲染问题的后期修改。最终画面报告说明每个问题的修复方式，未解决项明确列出。

### G2. 导出

有匹配模板时建立名为 `Windows Desktop` 的导出预设，导出到 `build/neon_haven.exe`。

确认 JSON 注册表、字体、材质、lightmap 和所有运行资源都被导出。测试场景、制作脚本、原始 `.blend`、报告、录屏不进入发布包；地图通过字符串路径加载时，特别检查导出规则没有遗漏资源。

在运行目录中，不得依赖源码外的绝对路径。建议使用包含空格和中文的临时目录做一次实际启动。

```powershell
# 需要已经创建匹配预设、安装 4.7.2 导出模板，并建立 build 目录。
& $NeonGodotExe --headless --path . --export-release 'Windows Desktop' './build/neon_haven.exe'
```

模板不可用时，工程本身仍须完整，说明缺少什么、当前已验证到哪一步。不要自动用另一引擎版本导出掩盖问题。
